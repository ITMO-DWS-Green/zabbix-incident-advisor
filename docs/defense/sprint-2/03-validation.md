## Методика продолжения и время

Заданные в #99 сроки по Москве: план и первый результат — 25.11.2026 до 18:00, окончательный отчёт — 26.11.2026 до 12:00; защита — 27.11.2026. Соблюдение сроков не подтверждено.

**План:** уточнить согласованные критерии #97, согласовать один чистый стенд с Евгением и не запускать несовместимые сбои параллельно. Повторить E2E на том же SHA; при повторе отдельно зафиксировать карточку и привязку результата к новому событию. Для каждого запуска сохранить команду, версии и digest образов, commit test-server, конфигурацию, timestamps, логи/ссылку CI и ID события/инцидента. Compose ссылается на test-server `#main` и плавающие теги образов, поэтому одного SHA Advisor недостаточно для воспроизведения ([compose.yaml](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/blob/5ade5a747fa356273bc8d21f9c53a58265e5eae1/compose.yaml)).

Шаблон на согласованном чистом стенде: `ADVISOR_ANALYSIS_DELAY=20s docker compose --profile stand up -d --build`, дождаться успешного `setup`, затем `python infra/setup/e2e_test.py`; команды проверить для ОС и не выполнять до согласования стенда. Скрипт локального main задаёт `ERRORS_5XX`, `database`, rate 1.0, длительность 150 с, предварительно ждёт шесть минут здоровой истории. CI задаёт задержку анализа 20 с; значение Compose по умолчанию — 60 с. Текущий скрипт ищет `DONE`/`5xx` и сообщения заглушки без привязки к времени запуска, поэтому для повторов нужны изоляция либо отдельная проверка ID и timestamps; автоматический успех не заменяет проверку карточки.

**Время — не подтверждено.** Для замера отдельно фиксировать начало события Zabbix и время реально появившегося комментария, с указанием источника часов и погрешности опроса; для времени анализа — начало сбора/конвейера и момент завершения/сохранения. В локальном main `AnalysisService` получает `now` **до** построения графа и анализа и записывает его как `analyzedAt`; поэтому расчёт evaluator от начала сбоя до `analyzedAt` не подтверждает время завершения анализа или публикации. [AnalysisService](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/blob/5ade5a747fa356273bc8d21f9c53a58265e5eae1/service/app/src/main/java/ru/itmo/advisor/app/incident/AnalysisService.java), [evaluator](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/blob/5ade5a747fa356273bc8d21f9c53a58265e5eae1/service/analysis-evaluation/src/main/java/ru/itmo/advisor/analysis/evaluation/TimeOverlapEvaluator.java). Никакой SLA времени старта или доставки не заявляется.

## Выводы для защиты и передача

1. **Подтверждено метаданными CI:** на зафиксированном в #98 техническом SHA прошли сборка и один сквозной job; E2E проверял `database` на первом месте и наличие маркера в комментарии к выбранному инциденту. Привязка всех результатов к новому событию и содержимое исходных логов не подтверждены.
2. **Подтверждено локальным JUnit:** один граничный тест на исходниках `5ade5a7` прошёл; это не штатная Gradle-сборка и не повтор E2E. **Не подтверждено:** браузерная карточка, повтор основного пути на том же SHA и доставка в реальный Telegram. Успешный PR run использует другой SHA и не фиксирует внешние зависимости.
3. **Подтверждено по коду среза:** `analyzedAt` фиксируется до выполнения разбора; совпадение сбоев evaluator по времени может повторно использовать один инцидент. Не использовать эти показатели как подтверждение времени завершения или точности сопоставления.
4. **Не установлено:** согласование критериев заказчиком. 70%/90% — черновые цели; единичный CI-сценарий и исторический пример не позволяют оценить генеральную выборку. В историческом примере источник был четвёртым; результаты разных версий не объединять.

**Передача — подготовлено, подтверждения получения нет.** Публичный [PR #103](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/pull/103) с комплектом #101 на момент проверки открыт. Для адресатов подготовлены конкретные поправки:

Доступный отдельный граничный результат — [один тест JUnit](evidence/03-boundary-junit-20261126.txt), не повтор E2E. Реальный Telegram и время до готового разбора не подтверждены.
