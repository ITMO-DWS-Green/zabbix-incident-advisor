# Разработка

## Правила зависимостей

- `analysis-*` зависят **только** от `domain`. Нужно что-то ещё (Zabbix, БД) — значит, нужен новый метод в интерфейсе `domain` или новое поле в `IncidentContext`. Это отдельный PR с предупреждением в чате команды: изменение `domain` затрагивает всех.
- Spring — только в `app`. Бизнес-логика — обычные классы, тестируются без контекста.
- Реализации выбираются в одном месте: `app/.../config/BusinessLogicConfig.java`.
- Изменения в Zabbix (комментарии, триггеры, значения) — только через `ZabbixWriter`. Изменения правил — только после подтверждения человеком.

## Модель данных

| Класс | Что это |
|---|---|
| `Incident` | Группа связанных проблем — один разбор. Шапка сводит проблемы: `problemEventId` и `startedAt` — первой, хосты и теги — всех, важность — наибольшая; статус разбора и сам разбор |
| `Problem` | Проблема Zabbix внутри инцидента: `eventId`, триггер, хосты, начало, закрытие |
| `IncidentContext` | Всё для разбора: окно времени, карта связей, сервисы в разборе (`scope`), `metrics` и `logs` по ним |
| `MetricSeries` | История числового элемента за окно: `MonitoredItem` + точки; необязательные `trends` — часовые агрегаты UTC для сезонной нормы. Конструктор с двумя аргументами сохранён |
| `LogSeries` | Строки лог-элемента за окно. Лог-элемент — тип «лог» или текстовый с тегом `component: logs` |
| `ServiceGraph` | Кто от кого зависит; `neighbourhood`, `dependencies`, `dependents` |
| `MetricDeviation` | Отклонение метрики: было, стало, **когда началось**, сила |
| `LogEvidence` | Характерная строка: шаблон, пример, сколько раз, новая ли |
| `Suspect` | Подозреваемый: сервис, оценка, когда отклонился, причины — список по убыванию вероятности |
| `Explanation` | `summary` (уходит в Zabbix), `details` (Markdown для карточки), кто написал |
| `AnalysisResult` | Всё вместе; хранится в БД целиком (JSONB) |
| `FaultLabel` | Разметка сбоя от test-server — эталон для оценки |

## Объединение проблем в инцидент

`IncidentService` на каждую проблему из коннектора спрашивает `IncidentMergePolicy` (реализация — `GraphWindowMergePolicy` в `analysis-ranking`):

- проблема входит в открытый инцидент, если её хост совпадает с хостом инцидента или связан с ним цепочкой `depends_on` в любую сторону, и началась не дальше `ADVISOR_INCIDENT_MERGE_WINDOW` (60 с) от начала инцидента;
- окно отсчитывается от начала инцидента, а не от последней проблемы — иначе каскад поглотит и независимый сбой, начавшийся позже (плейбук `two-incidents`);
- **поздняя причина**: проблема на сервисе, от которого зависят хосты ещё открытых проблем инцидента, присоединяется и позже окна — до `2 × окно`. Так бывает, когда источник упал: зависимые сразу ловят 5xx, а у него самого срабатывает только «нет ответа больше минуты». Поздний сбой на *зависимом* сервисе — отдельный инцидент;
- карта связей для объединения кэшируется (`ServiceGraphCache`) и обновляется в фоне раз в минуту: приём коннектора не ждёт Zabbix API. Без карты объединяются только проблемы одного хоста;
- разбор запускается один раз — при создании инцидента; в него попадают хосты всех проблем. Комментарий пишется к каждой проблеме; проблема, присоединившаяся к уже разобранному инциденту, получает готовый разбор без повторного запуска;
- инцидент закрывается, когда закрыты все его проблемы.

## Догон пропущенных событий

`CatchUpService` при старте и раз в `ADVISOR_INCIDENT_CATCH_UP_INTERVAL` (5 мин, `0` — выкл.) берёт `problem.get` (`recent=true`) и:

- проблемы, которых нет в базе, дополняет хостами и тегами через `event.get` и отдаёт в `IncidentService.onEvents` — те же слияние в инцидент и защита от дублей, что у коннектора, поэтому одновременная доставка не создаёт копий;
- открытые у нас проблемы, закрытые в Zabbix, закрывает по `r_eventid` (если `problem.get` их уже не показывает — через `event.get`).

Граница: восстанавливается то, что видит `problem.get` — открытые и недавно закрытые проблемы. Сбой, целиком начавшийся и закончившийся за простой дольше окна `recent`, не восстанавливается. Если Zabbix недоступен, сверка пишет предупреждение и повторяется через интервал.

## Конвейер

`app/.../incident/AnalysisService.java`:

```
ServiceGraphProvider.build(хосты Zabbix)
ContextSource.load(инцидент, граф)        ← история из Zabbix API, готово
MetricDeviationDetector.detect(контекст)
LogEvidenceExtractor.extract(контекст)
SuspectRanker.rank(контекст, отклонения, логи)
ExplanationWriter.write(...)
→ сохранить → комментарий к каждой проблеме в Zabbix → CauseSymptomPolicy → отметка симптома
```

Ошибка в любом шаге — разбор `FAILED` с текстом ошибки; в интерфейсе видно, что сломалось. Ошибка записи в Zabbix разбор не отменяет.

## Доказательства из логов

`PatternLogEvidenceExtractor` (`analysis-logs`) берёт строки из `IncidentContext.logs()`:

- уровень и сообщение разбираются из текста строки (формат файла test-server: `дата УРОВЕНЬ [сервис] [trace] логгер - сообщение`); у файловых элементов `log[]` поле severity в Zabbix пустое. INFO и ниже отбрасываются;
- сообщение приводится к шаблону: числа, UUID, время, IP, hex-id → `<N>`, `<UUID>`, `<TIME>`, `<IP>`, `<HEX>`; префикс (время, trace id) в шаблон не входит, поэтому строки разных запросов считаются вместе;
- шаблоны считаются до и после `startedAt − 5 мин` — той же границы, что у `BaselineDeviationDetector`: проблема в Zabbix появляется позже самого сбоя, и первые ошибки старше `startedAt`;
- в доказательства идут шаблоны, которых не было до границы (`newInWindow`), и те, что участились в 5 раз и больше (не меньше 3 повторов в окне);
- если на сервисе нет ни новых, ни участившихся шаблонов (тот же сбой повторился через несколько минут после прошлого, и его строки уже в базовой линии), берутся его частые ERROR — не меньше 3 повторов в окне, без отметки «новая»;
- пример — настоящая первая строка шаблона в окне; на сервис не больше 5 шаблонов, ERROR раньше WARN. Строка без распознанного уровня годится, только если она новая или участилась.

Строки логов `ZabbixContextSource` запрашивает по одному элементу и берёт самые свежие `advisor.analysis.history-limit` (20 000) — `ZabbixApi.latestHistory`. Шумный сбой даёт десятки тысяч строк; с общим лимитом от начала окна сам сбой в разбор не попадал.

Ограничение: если у лог-элемента до границы вообще нет строк (агент только запущен), все шаблоны WARN и ERROR считаются новыми.

## Как тестировать свой модуль

Собрать `IncidentContext` руками и проверить результат — пример в `app/src/test/.../AnalysisServiceTest.java`: каскад «database тормозит → orders и gateway ошибаются» и ожидание, что первым подозреваемым будет database.

Проверка на живых данных: поднять `docker compose --profile stand up -d --build`, включить сбой на панели стенда, посмотреть карточку в Zabbix, оценку точности — `GET /api/evaluation`.

## Детектор метрик и ранжирование (#8, #9)

В `BusinessLogicConfig` подключены `RobustDeviationDetector` и `GraphEvidenceRanker`.

- Норма метрик считается по истории **до начала инцидента минус 5 минут**: устойчивый линейный тренд Theil–Sen (не более 32 опорных точек), медиана остатков и `1.4826 × MAD`. Обычный рост счётчика не считается сбоем, а скачок относительно тренда — считается. Эта граница оставляет место для задержки триггера Zabbix. Нужно не меньше пяти конечных значений.
- Масштаб отклонения — максимум из MAD, 5% абсолютной нормы и `1e-9` для нулевой нормы. Это безразмерная оценка, сопоставимая при смене единиц выше численного порога. Отклонение подтверждают три последовательные точки с оценкой больше 3.5 в одну сторону; началом считается первая из них. Нормальная/нечисловая точка, смена направления и разрыв больше трёх обычных интервалов сбрасывают подтверждение. Дубликаты времени не добавляют подтверждений.
- `ZabbixContextSource` загружает до 28 дней завершённых часовых трендов до той же границы, по 20 элементов за запрос. При недоступном `trend.get` анализ продолжает работать по сырой истории; ошибки обязательной истории по-прежнему прерывают анализ.
- Для сезонности сначала используется тот же день недели и час UTC (не менее трёх исторических часов), затем тот же час разных дней (не менее семи). Медиана остатков сырой истории корректирует локальное смещение; MAD остатков и диапазоны часовых агрегатов учитывают шум. Если данных недостаточно — обычная локальная норма. Агрегаты, перекрывающие границу сбоя, и будущие значения исключены.
- В ранжирование входят только сервисы с доказательствами в области разбора. Направление `A → B` означает, что A зависит от B. Поддерживается транзитивное распространение; циклы не дают преимущества ни одному участнику. Здоровая зависимость без доказательств не становится подозреваемой только из-за графа.
- Оценка: `0.25 × время + 0.20 × сила + 0.15 × логи + 0.40 × граф`, минус 0.25 для возможного симптома зависимости; результат ограничен `[0, 1]`. Это эвристический балл, **не вероятность**. Время сравнивается внутри связной группы, поэтому ранний независимый сбой не понижает другую группу. Допуск в 60 секунд учитывает разный шаг наблюдений причины и симптома.
- Причины перечисляют реальные метрики, зависимости и количество строк шаблона лога. При полном отсутствии доказательств возвращаются хосты проблемы с оценкой 0.1 и явным пояснением недостатка данных. Новый шаблон лога может датировать сбой; первая строка старого шаблона не считается временем учащения ошибок.

Ограничения: сезонность привязана к UTC (переходы местного летнего времени не моделируются), короткие всплески короче трёх измерений намеренно отбрасываются. При отсутствии достаточной истории детектор не делает предположений. Старые `BaselineDeviationDetector` и `EarliestDeviationRanker` оставлены как образцы, но не подключены.

Проверки: `RobustDeviationDetectorTest`, `GraphEvidenceRankerTest`, загрузка/отказ трендов в `ZabbixContextSourceTest`, каскад в `AnalysisServiceTest`. Сквозной тест сначала собирает шесть минут здоровой истории, затем требует отклонение database и его первое место в разборе реального сбоя.

## LLM

- По умолчанию `stub`: модели нет, `ExplanationWriter` пишет по шаблону. Ничего не уходит наружу.
- `ADVISOR_LLM_PROVIDER=openai` — любой OpenAI-совместимый API. Локально: `--profile ollama`.
- Каждый вызов проходит маскирование (IP, e-mail, URL и слова из `Request.sensitive` → псевдонимы) и пишется в таблицу `llm_audit` в замаскированном виде.
- LLM только пересказывает найденные факты. Искать причину — задача детекторов и ранжирования.

## Где что в Zabbix

| Что | Как настроено |
|---|---|
| Токен API сервиса | `setup.py` создаёт API-токен для Admin и пишет его в общий том `/secrets` |
| Коннектор событий | Все события → `/zabbix/connector/events`, Bearer-токен |
| Коннектор значений | Элементы с тегом `advisor` → `/zabbix/connector/values` |
| Модуль интерфейса | Папка смонтирована в zabbix-web, модуль включён через `module.create` |
| Хосты стенда | Группа `test-server`, теги `depends_on`, метрики, триггеры и лог-элемент `log[…]` (его читает `zabbix-agent2` из общего тома `stand-logs`) |
| Кэш конфигурации | `ZBX_CACHEUPDATEFREQUENCY=10` — новые триггеры работают через 10 с |

Для боевого Zabbix: отдельный пользователь с правами чтения на нужные группы и записи триггеров, свой API-токен, свои секреты `ADVISOR_UI_TOKEN` и `ADVISOR_CONNECTOR_TOKEN`, адрес сервиса в `zabbix-module/incident-advisor/config.php`.

Точки расширения Zabbix и API в целом — [architecture/zabbix-integration.md](architecture/zabbix-integration.md), обзор — [docs/README.md](README.md).

В ранжировании старое отклонение одной метрики не исключает зависимость, которая объясняет более поздние отклонения или новые шаблоны логов того же сервиса. Проверяется время отдельных признаков; самый ранний признак остаётся в результате и объяснении.
