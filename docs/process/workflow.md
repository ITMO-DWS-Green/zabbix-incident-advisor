# Как работаем

## Код
Trunk-based development ([D-001](../architecture/decisions.md)): ветка от свежего `main` под задачу, слияние через Pull Request с одним аппрувом и зелёным CI, ветку после слияния удаляем.

- Имя ветки: `<тип>/<номер задачи>-<кратко>`, тип — `feature`, `fix`, `spike`, `docs`, `infra`. Пример: `feature/8-metrics-detector`. Автоматически не проверяется (нужен Enterprise) — следим на ревью.
- В описании PR — `Closes #N`, чтобы задача закрылась сама.
- CI на каждый PR и на push в `main`, но только то, что нужно:
  - сборка и тесты — если менялся `service/`;
  - сквозная проверка на живом Zabbix (~10 мин) — если менялся код сервиса (не тесты), модуль интерфейса, `infra/`, `compose.yaml` или CI;
  - PR только с документацией проходит без запусков; пропущенная проверка считается пройденной;
  - всё сразу — вручную: Actions → CI → Run workflow.
- Оповещения о задачах, PR, ревью и упавшем CI приходят в Telegram во все чаты, куда добавлен бот (`.github/workflows/telegram.yml`). Новый чат подхватывается при следующем событии или в течение 6 часов; убрали бота — рассылка туда прекращается.
- Как писать свой модуль — [development.md](../development.md).

## Задачи
- Любая работа — задача в [Issues](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues).
- У задачи есть метка области и спринт (milestone) — или метка очереди, если в спринт не взята.
- Описание: «Зачем», «Что сделать», «Где», чек-лист «Готово, когда», «Зависит от».

| Метка | Область |
|---|---|
| `metrics` | `analysis-metrics`: отклонения метрик |
| `logs` | `analysis-logs` и логи стенда |
| `ranking` | `analysis-ranking`: подозреваемые, причина и симптомы, объединение в инцидент |
| `explain` | `analysis-explain`: объяснение |
| `graph` | `analysis-graph`: карта связей |
| `evaluation` | `analysis-evaluation`: точность на стенде |
| `stream` | `analysis-stream`: поток значений |
| `llm` | LLM, маскирование, журнал |
| `ui` | Модуль интерфейса Zabbix |
| `zabbix` | Настройка Zabbix, API, коннекторы, действия |
| `infra` | Compose, CI, стенд, эксплуатация |
| `test` | Тесты |
| `docs` | Документация, демо |
| `требования` | Требования, заказчик, критерии приёмки |
| `spike` | Нужно разобраться перед реализацией |
| `P1`, `P2`, `P3` | Приоритет внутри спринта: критично, важно, можно сдвинуть. Порядок — в описании milestone |
| `очередь 2`, `очередь 3`, `эксплуатация` | Не взято в спринт: после MVP, после защиты, для боевой установки |

## Доска
Backlog → Ready → In progress → In review → Done. Берём задачи из Ready; в работе у одного человека — не больше одной-двух задач.

## Встречи и Telegram
- Встреча — задача с меткой `встреча`: New issue → **Встреча**. В поле «Когда» — расписание обычными словами: «каждый вторник 12:15», «пн, чт 19:00», «каждые 2 недели по пятницам 16:00 с 07.11.2026», «05.11.2026 18:00», «27.11.2026» (без времени — встреча на весь день). Время московское.
- Бот напоминает в Telegram за сутки (с повесткой), за час и за 15 минут. За 15 минут тегает администраторов чата и всех, кто написал боту `/join`. Закрыли задачу — напоминаний нет; поменяли время или повестку в задаче — бот берёт новое.
- Команды бота в чате: `/join`, `/leave` — тегать меня или нет; `/github` — писать оповещения GitHub в эту тему; `/meetings` — писать напоминания в эту тему; `/off` — не писать в этот чат вообще, `/on` — снова писать. В группе с темами команду пишут внутри нужной темы.
- Бот пишет во все чаты, куда его добавили. Секрет репозитория `TELEGRAM_BOT_TOKEN` обязателен.

## Definition of Done
- [ ] выполнены все пункты «Готово, когда» в задаче;
- [ ] код в `main` через PR с аппрувом;
- [ ] CI зелёный, есть тесты на новую логику;
- [ ] если изменились термины, требования или решения — обновлена база знаний.
