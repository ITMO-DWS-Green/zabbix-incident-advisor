## D-004. Делаем расширение Zabbix, а не свою систему мониторинга
Статус: принято командой, согласование с заказчиком — [#1](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/1) · Дата: 2026-10-26 · Кто: предложил Евгений Матеюк
Контекст: каркас спринта 1 повторял Zabbix — свой приём, хранение, правила, интерфейс. Такая система была бы хуже готовых, и её никто не стал бы внедрять.
Решение: расширение рядом с Zabbix 7.0 LTS без изменения ядра. Zabbix собирает данные и открывает проблемы, мы делаем разбор причины и возвращаем его в Zabbix и Telegram.
Альтернативы: своя система мониторинга (каркас спринта 1) — дублирует Zabbix; доработка ядра Zabbix — огромная кодовая база на C, долго и рискованно; надстройка над Prometheus и Grafana — команда изучила Zabbix, и в нём есть коннекторы и модули интерфейса.
Последствия: требования переписаны ([functional.md](../requirements/functional.md)); «два подхода» — наш разбор против первого сработавшего триггера; ML — опционально.

## D-005. Логи test-server попадают в Zabbix через агент
Статус: предложено, проверяем в [#6](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/6) · Дата: 2026-10-27
Контекст: доказательства из логов (FR-06) читаются из лог-элементов Zabbix, а test-server пишет логи только в консоль.
Решение: test-server дополнительно пишет лог в файл на общий том; Zabbix agent 2 читает его активной проверкой `log[...]`. Так логи попадают в Zabbix тем же путём, что и у реальных пользователей.
Альтернативы: test-server отправляет строки в элементы-ловушки через `history.push` — проще в Docker, но так в жизни никто не делает.
Последствия: в стенде нужен том логов у agent 2, в скрипте настройки — лог-элементы на каждый хост.

## D-006. Оповещение — через действие Zabbix в групповой чат команды Telegram
Статус: предложено, делаем в [#17](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/17) · Дата: 2026-10-27
Контекст: заказчик хочет, чтобы при сбое собиралась ответственная команда. Бот Telegram не может сам создавать группы.
Решение: у каждой команды заранее есть групповой чат с ботом. Справочник «сервис — команда» — тег `team` у хоста. Наш сервис пишет разбор комментарием к проблеме, действие Zabbix по тегу `team` отправляет его в чат команды штатным типом оповещения Telegram.
Альтернативы: свой бот в сервисе — больше кода, дублирует оповещения Zabbix; другие мессенджеры — позже, тем же способом.
Последствия: в сервисе нет кода отправки в мессенджер; настройка действий — в скрипте настройки стенда.

## D-007. Своя БД — только для инцидентов, разборов и оценок
Статус: принято, реализовано в каркасе · Дата: 2026-10-27
Решение: метрики и логи храним только в Zabbix. Своя PostgreSQL (отдельная база) хранит инциденты, разборы, оценки инженеров, разметку и журнал LLM. Схема — Flyway, результат разбора — JSONB.
Последствия: заменяет хранилище в памяти из каркаса спринта 1.

## D-009. Новый репозиторий и модуль на каждую идею
Статус: принято, ревью — [#3](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/3) · Дата: 2026-10-28 · Кто: Евгений Матеюк
Контекст: чтобы пять человек писали разбор параллельно, каждому нужен свой модуль, который не зависит от Zabbix, БД и чужого кода.
Решение: репозиторий [zabbix-incident-advisor](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor) вместо log-collector (тот в архиве). Сервис — многомодульный Gradle: `zabbix-client`, `domain`, `llm`, `analysis-*` по одному на идею, `app`. Модули `analysis-*` зависят только от `domain` и получают данные аргументами. Реализации выбираются в `BusinessLogicConfig`.
Альтернативы: один модуль `analysis` — постоянные конфликты при слиянии; порты в `core` как в log-collector — та же идея, но без готовой инфраструктуры.
Последствия: изменение `domain` затрагивает всех — отдельным PR; заглушки и образцы позволяют собирать и тестировать всё с первого дня.

## D-010. Карта связей — тег `depends_on`
Статус: принято · Дата: 2026-10-28
Решение: у хоста тег `depends_on` со списком сервисов через запятую, от которых он зависит (gateway → `orders`). Тег `team` — для оповещения. В log-collector предлагался тег `calls` — смысл тот же, название выбрано по направлению зависимости.
Последствия: в реальном Zabbix тегов может не быть — связи из логов и истории в [#14](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/14).

## D-011. Разбор через задержку после начала проблемы
Статус: предложено · Дата: 2026-10-28
Контекст: в первые секунды проблемы ещё не сработали триггеры соседей и в истории нет точек после начала.
Решение: разбор запускается через `ADVISOR_ANALYSIS_DELAY` (по умолчанию 60 с) после начала проблемы; окно истории — `ADVISOR_ANALYSIS_LOOKBACK` (15 мин) до начала. Разбор можно перезапустить кнопкой.
Последствия: конфликтует с порогом «комментарий ≤ 60 с» — [вопрос](../requirements/open-questions.md).

## D-012. LLM необязательна, маскирование и журнал встроены
Статус: предложено, выбор модели — [#5](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/5) · Дата: 2026-10-28
Решение: по умолчанию LLM выключена (`stub`), объяснение пишется по шаблону. Включается любой OpenAI-совместимый API, в том числе локальная Ollama. Каждый вызов проходит маскирование (имена хостов, IP, URL, e-mail → псевдонимы) и пишется в `llm_audit`. LLM только пересказывает найденные факты, причину ищут детекторы и ранжирование.
Последствия: решение работает без LLM; данные наружу уходят только по явной настройке.

## D-013. Модуль интерфейса ходит в сервис через PHP-прокси
Статус: принято · Дата: 2026-10-28
Решение: JS модуля обращается к действиям `incidentadvisor.api.get` / `.post`, PHP пересылает запрос в сервис с секретом `X-Advisor-Token` и именем пользователя Zabbix. Пропускаются только пути `/api/…`.
Альтернативы: JS напрямую в сервис — нужен CORS и своя авторизация.
Последствия: права и сессия — как у пользователя Zabbix; сервис не открыт браузеру.
