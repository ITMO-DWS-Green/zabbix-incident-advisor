# Критерии приёмки

**Предложение для согласования с заказчиком.** Решение по требованиям — [#1](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/1), решение по порогам — [#2](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/2).

## Метрики и предлагаемые пороги

| Метрика | Как считаем | Предложение для защиты |
|---|---|---|
| Top-1 | Доля размеченных сбоев, у которых настоящий источник стоит первым в списке подозреваемых | ≥ 70% и выше, чем у штатных триггеров на тех же прогонах |
| Top-3 | Доля размеченных сбоев, у которых настоящий источник входит в первую тройку | ≥ 90% |
| Своевременный top-1 на каскадах | Доля каскадных сбоев, у которых настоящий источник стоит первым, а разбор готов в пределах 180 с | ≥ 70% |
| Время до готового разбора | От начала сбоя по разметке до `analysis.completedAt` в первом сохранённом разборе. Отдельно показываем время от открытия проблемы Zabbix до той же точки | Показываем медиану, 95-й перцентиль и число разборов, по которым удалось измерить время |

Знаменатель для top-1 и top-3 — все размеченные сбои набора. Пропуски и разборы без подозреваемых дают ноль верных ответов. Для своевременного top-1 берём все сбои с ожидаемым каскадом. Балл даёт только верный первый ответ с известным временем готовности в пределах порога. Пропуски и лишние инциденты показываем отдельными счётчиками.

`analysis.completedAt` фиксируется после чтения контекста, вычислений и подготовки объяснения. Разбор засчитывается после успешного сохранения со статусом `DONE`. Для старых разборов, у которых есть только время старта `analysis.analyzedAt`, время готовности неизвестно. Ручной повторный разбор в замер первого ответа не входит. Для комментария фиксируем отдельный показатель от события до первого комментария Advisor по `event.get → acknowledges.clock`. При сбое публикации отмечаем, что комментария нет.

## Эталонные прогоны

| Плейбук test-server | Размеченные сбои за один прогон | Что проверяем |
|---|---|---|
| [`cascade-database`](https://github.com/ITMO-DWS-Green/test-server/blob/main/playbooks/cascade-database.json) | Задержка на `database` | Несколько проблем образуют один инцидент с источником на `database` |
| [`payments-errors-then-crash`](https://github.com/ITMO-DWS-Green/test-server/blob/main/playbooks/payments-errors-then-crash.json) | Всплеск 5xx, затем падение процесса `payments` | Обнаружены два отдельных инцидента с источником на `payments` |
| [`two-incidents`](https://github.com/ITMO-DWS-Green/test-server/blob/main/playbooks/two-incidents.json) | 5xx на `database` и утечка памяти на `gateway` с перекрытием | Два отдельных инцидента с двумя разными источниками. Текущая настройка стенда не даёт сигнала о памяти, этот пробел нужно закрыть перед приёмкой |

План для защиты — четыре прогона каждого эталонного плейбука, всего 20 размеченных сбоев. [`all-fault-types`](https://github.com/ITMO-DWS-Green/test-server/blob/main/playbooks/all-fault-types.json) используем дополнительно, чтобы показать, какие типы сбоев покрыты. Между прогонами ждём закрытия проблем предыдущего прогона. В отчёте сохраняем `scenarioId`, версии Advisor и test-server, настройки, интервал прогона и исходные результаты.

Соответствие между сбоями и результатами устанавливаем по времени до сравнения подозреваемых. Событие открытия должно попадать в интервал от начала сбоя до двух минут после его конца. При перекрытиях выбираем максимальное число непересекающихся пар с наименьшей суммарной задержкой от начала сбоя. При равенстве упорядочиваем по времени и стабильным идентификаторам. Один инцидент или эпизод триггеров засчитывается максимум для одного сбоя. Другие инциденты в интервале прогона считаем лишними. Разметка используется только при оценке.

## Базовая линия Zabbix

1. **Штатные триггеры.** Сохраняем события по хостам стенда из `event.get`. Для сравнения объединяем проблемы по тем же правилам близости по времени и связям сервисов. Ранжируем хосты по времени первого срабатывания триггера. Считаем те же top-1, top-3, пропуски и лишние эпизоды на тех же сбоях. Время сигнала — момент первого срабатывания, отдельно от времени готовности объяснения Advisor. На стенде проверяются доступность, отсутствие данных, доля 4xx/5xx и задержка.
2. **Триггеры на трендах.** Отдельный сравнительный прогон на тех же плейбуках с прогретой историей. Предлагаем применить следующие выражения к `testserver.error_rate` и `testserver.latency` каждого хоста.

   - `baselinedev(/database/testserver.error_rate,1h:now/h,"h",6) >= 3` — отклонение последнего завершённого часа от шести предыдущих часовых сезонов.
   - `trendstl(/database/testserver.error_rate,24h:now/h,1h,2h) > 0` — аномалия последнего часа по 24 часам истории и сезонности 2 ч.

   Фиксируем параметры до прогона. Для каждого сбоя записываем, был ли сигнал, на каком хосте и когда он появился. Отдельно отмечаем недостаток данных и случаи, когда вычисление недоступно. Пригодность функций для минутных сбоев оцениваем с учётом часовых агрегатов. [Документация функций трендов Zabbix 7.0](https://www.zabbix.com/documentation/7.0/en/manual/appendix/functions/trends)

`GET /api/evaluation?scenarioId=…` предоставляет предварительный отчёт. Текущее сопоставление по времени может учесть один инцидент в нескольких пересекающихся окнах. Воспроизводимый прогон с однозначным сопоставлением и сравнением базовой линии — [#15](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/15).

## Планирование и сквозная проверка

Задержка старта разбора по умолчанию — 60 с от события, открывшего инцидент. Если событие пришло через 45 с, остаётся подождать 15 с. Когда окно уже прошло, разбор сразу ставится в очередь. После перезапуска действует то же правило. Время после постановки в очередь включает выполнение разбора, а публикация замеряется отдельно.

Сквозной тест `infra/setup/e2e_test.py` использует тот же Compose и задержку 60 с по умолчанию, что и локальный запуск. Для контрольного каскада он проверяет готовность разбора не позже 180 с от события, наличие комментария и наличие времени до ответа в отчёте для этого прогона. Пороги качества для защиты относятся ко всему эталонному набору.

## MVP готов, когда
- [ ] Каждый сбой из плейбука сохраняется с разметкой: сценарий, тип, сервис-источник, начало, конец.
- [ ] На один сбой создаётся один инцидент, даже если триггеры сработали у нескольких сервисов (`cascade-database`).
- [ ] Два независимых сбоя дают два инцидента (`two-incidents`).
- [ ] На эталонных прогонах достигнуты согласованные пороги top-1, top-3 и своевременного top-1 на каскадах.
- [ ] Есть сравнение с базовой линией на тех же сбоях, Advisor чаще называет источник первым.
- [ ] Разбор появляется комментарием к проблеме в Zabbix, задержка публикации измерена отдельно.
- [ ] В разборе есть источник, отклонившиеся метрики и не меньше двух характерных строк логов.
- [ ] Сообщение с разбором приходит в Telegram-чат команды, отвечающей за сервис-источник.
- [ ] В интерфейсе Zabbix открываются карточка инцидента и страница точности.
- [ ] Результаты прогонов сохранены в репозитории и воспроизводятся.
