# Критерии приёмки

Статус: **черновик**, согласование с заказчиком — [#2](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/2). Пороговые значения — предложение команды.

## Как проверяем
Поднимаем стенд одной командой, запускаем плейбуки test-server (`cascade-database`, `payments-errors-then-crash`, `all-fault-types`, `two-incidents`) и сверяем результат разбора с разметкой сбоев: `GET /api/evaluation?scenarioId=…`. Часть проверок автоматизирована в сквозном тесте CI (`infra/setup/e2e_test.py`).

## MVP готов, когда
- [ ] Каждый сбой из плейбука сохраняется с разметкой: сценарий, тип, сервис-источник, начало, конец.
- [ ] На один сбой создаётся один инцидент, даже если триггеры сработали у нескольких сервисов (`cascade-database`).
- [ ] Два независимых сбоя дают два инцидента (`two-incidents`).
- [ ] Настоящий источник назван первым в ≥ 70% инцидентов и входит в первые три в ≥ 90%.
- [ ] Наш разбор называет источник верно чаще, чем базовый подход «первый сработавший триггер».
- [ ] Разбор появляется комментарием к проблеме в Zabbix не позже чем через 60 с после события.
- [ ] В разборе есть источник, отклонившиеся метрики и не меньше двух характерных строк логов.
- [ ] Сообщение с разбором приходит в Telegram-чат команды, отвечающей за сервис-источник.
- [ ] В интерфейсе Zabbix открываются карточка инцидента и страница точности.
- [ ] Результаты прогонов сохранены в репозитории и воспроизводятся.

## Что уже проверяет CI
- [x] Стенд поднимается из `compose.yaml`, Zabbix настраивается скриптом.
- [x] Сбой `ERRORS_5XX` на `database` даёт инцидент с готовым разбором.
- [x] Разбор появляется комментарием к проблеме в Zabbix.
- [x] Модуль открывается в Zabbix и проксирует запросы в сервис.
- [x] Разметка сбоя доходит до сервиса и учитывается в отчёте о точности.
