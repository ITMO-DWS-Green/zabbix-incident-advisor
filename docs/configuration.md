# Настройки сервиса

Значения по умолчанию заданы в [`application.yml`](../service/app/src/main/resources/application.yml) и [`AdvisorProperties`](../service/app/src/main/java/ru/itmo/advisor/app/config/AdvisorProperties.java). Для запуска через Compose переменная должна быть передана в окружение контейнера; текущий набор — в [`compose.yaml`](../compose.yaml).

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `ADVISOR_ANALYSIS_DELAY` | `60s` | задержка перед разбором после приёма новой проблемы |
| `ADVISOR_ANALYSIS_LOOKBACK` | `15m` | сколько истории до начала брать в разбор |
| `ADVISOR_ANALYSIS_GRAPH_DEPTH` | `2` | насколько далеко по карте связей брать соседей |
| `ADVISOR_INCIDENT_CATCH_UP_INTERVAL` | `5m` | как часто сверять `problem.get` с базой, чтобы догнать события, которые коннектор не доставил (первая сверка — при старте); `0` — выключить |
| `ADVISOR_INCIDENT_MERGE_WINDOW` | `60s` | окно объединения: проблема на связанном сервисе, начавшаяся не дальше этого от начала инцидента, входит в него; `0` — не объединять |
| `ADVISOR_RETENTION_INCIDENTS` | `90d` | срок хранения инцидента после закрытия |
| `ADVISOR_RETENTION_LLM_AUDIT` | `90d` | срок хранения записи журнала LLM с момента её создания |
| `ADVISOR_ZABBIX_COMMENT` | `true` | писать ли разбор комментарием к проблеме |
| `ADVISOR_LLM_PROVIDER` | `stub` | `stub` — без модели; `openai` — OpenAI-совместимый Chat Completions API |
| `ADVISOR_LLM_BASE_URL` | `http://ollama:11434/v1` | базовый адрес API без `/chat/completions`: Ollama, OpenRouter, Groq, LM Studio и др. |
| `ADVISOR_LLM_MODEL` | `qwen2.5:3b` | имя модели у выбранного провайдера |
| `ADVISOR_LLM_API_KEY` | — | ключ провайдера; для локальной Ollama можно оставить пустым |
| `ADVISOR_UI_TOKEN` | `dev-ui-token` | секрет между модулем интерфейса и сервисом |
| `ADVISOR_CONNECTOR_TOKEN` | `dev-connector-token` | токен, с которым приходит коннектор Zabbix |
| `TELEGRAM_BOT_TOKEN` | — | токен бота для оповещения о разборе; задаётся контейнеру `setup`, в репозитории не хранится. Без него тип оповещения создаётся выключенным |
| `TELEGRAM_API_URL` | `https://api.telegram.org/bot` | куда вебхук шлёт сообщения; на стенде — заглушка `http://telegram-stub:8080/bot` |
| `TELEGRAM_CHAT_IDS` | — | id групповых чатов команд: `platform:-1001,orders:-1002,…`. Незаданная команда получает id-заглушку |

LLM выключена по умолчанию (`stub`). Чтобы подключить бесплатную/условно бесплатную нейронку, используйте OpenAI-compatible API:

```bash
# OpenRouter: бесплатные модели обычно имеют суффикс :free.
ADVISOR_LLM_PROVIDER=openai
ADVISOR_LLM_BASE_URL=https://openrouter.ai/api/v1
ADVISOR_LLM_MODEL=meta-llama/llama-3.2-3b-instruct:free
ADVISOR_LLM_API_KEY=<ключ OpenRouter>

# Groq: бесплатные лимиты зависят от аккаунта.
ADVISOR_LLM_PROVIDER=openai
ADVISOR_LLM_BASE_URL=https://api.groq.com/openai/v1
ADVISOR_LLM_MODEL=llama-3.1-8b-instant
ADVISOR_LLM_API_KEY=<ключ Groq>
```

Проверить OpenRouter-ключ можно без запуска стенда: `ADVISOR_LLM_API_KEY=<ключ> python3 .github/scripts/check_openrouter.py`. В GitHub Actions положите ключ в repository secret `OPENROUTER_API_KEY` и запустите workflow **CI** с включённым параметром `openrouter_check` вручную.

Локально можно использовать профиль Ollama: [инструкция запуска](getting-started.md). Значение в таблице — резервное значение Java-сервиса; [`.env.example`](../.env.example) содержит готовые примеры. Перед внешней LLM факты инцидента проходят маскирование и пишутся в журнал `llm_audit`, но это всё равно внешний сервис — включайте его осознанно.

PHP-модуль читает `INCIDENT_ADVISOR_URL` и `INCIDENT_ADVISOR_TOKEN` из окружения `zabbix-web`. Его токен должен совпадать с `ADVISOR_UI_TOKEN` сервиса; исправление автоматической передачи через Compose отслеживается в [#82](https://github.com/ITMO-DWS-Green/zabbix-incident-advisor/issues/82).

В **Monitoring → Incident advisor → Хранение данных** администратор Zabbix может изменить оба срока. Сохранённые в базе значения имеют приоритет над переменными окружения и применяются при ближайшей очистке без перезапуска сервиса. До первого сохранения действуют значения из окружения.

В Compose отдельный токен для настроек создаёт контейнер `setup`. При установке вне Compose задай один и тот же секрет через `ADVISOR_RETENTION_ADMIN_TOKEN` в Java-сервисе и `INCIDENT_ADVISOR_RETENTION_TOKEN` в окружении PHP-модуля.

Очистка выполняется ежедневно в 03:00 UTC. Сроки хранения задаются положительными интервалами, например `30d` или `12h`. Открытые инциденты сохраняются до закрытия. Вместе с просроченным инцидентом удаляются его проблемы и оценки инженеров. Разметка стенда хранится отдельно.

## API сервиса

| Метод | Путь | Кто вызывает |
|---|---|---|
| POST | `/zabbix/connector/events` | коннектор Zabbix: события |
| POST | `/zabbix/connector/values` | коннектор Zabbix: значения элементов с тегом `advisor` |
| GET | `/api/incidents`, `/api/incidents/{id}` | модуль интерфейса |
| POST | `/api/incidents/{id}/reanalyze` | модуль: разобрать заново |
| POST | `/api/incidents/{id}/feedback` | модуль: «разбор верный / неверный» |
| GET | `/api/evaluation?scenarioId=` | точность на размеченных сбоях |
| POST, GET | `/api/evaluation/runs` | создать снимок по окну / список снимков |
| GET | `/api/evaluation/runs/{uuid}` | сохранённый снимок |
| GET | `/api/info` | состояние: Zabbix, LLM |
| GET, POST | `/api/settings/retention` | чтение и сохранение сроков хранения через прокси Zabbix администратором |
| POST | `/api/v1/labels` | test-server: разметка сбоя |

`POST /api/v1/labels` принимает `start` и `end` с наносекундной точностью в консервативном диапазоне от `0001-01-01T00:00:00Z` до `9999-12-31T23:59:59.999999Z` включительно. Вне диапазона возвращается 400 до округления и преобразования в JDBC, даже если округление вернуло бы значение внутрь диапазона; это ограничение API, а не полный диапазон PostgreSQL. Перед сохранением обе границы независимо округляются до ближайшей микросекунды; при остатке ровно 500 нс выбирается более поздний момент, в том числе до эпохи Unix. Исходное `end` должно быть не раньше `start`; округление сохраняет порядок. Повторы сравнивают каноническое `start` вместе с `scenarioId`, `type` и `source`: одинаковая идентичность обновляет `end`, чужая возвращает 409 без изменения записи. Пустые обязательные поля и некорректные интервалы возвращают 400.

Округление соответствует локально проверенным pgjdbc 42.7.5 и 42.7.10, которым старый `LabelRepository` передавал `Timestamp.from` без предварительного округления. Фактическая версия драйвера проекта и поведение других версий/конфигураций не подтверждены, поэтому полная совместимость со всеми ранее сохранёнными метками не гарантируется; при расхождении возможен 409, требуется проверка фактического драйвера и данных. Новая версия локально не деплоилась и реальные данные на ней не сохранялись.

`/api/evaluation` сравнивает advisor с baseline **на одном и том же выбранном инциденте**: для каждого сбоя выбирается первый по времени и id однозначно сопоставленный разобранный инцидент, независимо от эталона. Baseline — техническое имя хоста первой по времени проблемы этого инцидента; при нескольких одновременно первых проблемах все они должны иметь известный единственный общий технический хост. Если хост не определён однозначно, `baselineSource` и `baselineCorrect` равны `null`; при неизвестном эталоне `baselineCorrect` также равен `null`.

`baselineObservations` — число строк, где baseline можно сравнить с эталоном; `baselineCorrectCount` и `pairedAdvisorCorrectCount` — числа верных ответов baseline и advisor соответственно на этих же строках. Для процентов оба счётчика делятся на `baselineObservations`; при нулевом знаменателе интерфейс должен показывать «нет данных», а не 0%. Это условное парное сравнение только выбранных разобранных инцидентов, не самостоятельная оценка обнаружения baseline и не доказательство причинной связи. Данные передаются API; панель снимков показывает парные показатели baseline и advisor.

Для `/api/evaluation` действуют аварийные лимиты на выбранные данные: без `scenarioId` — на все метки и инциденты; с `scenarioId` — на метки сценария, инциденты в их окнах и метки других сценариев, пересекающие эти инциденты (для определения неоднозначности). Лимиты: 1000 labels, 1000 инцидентов, 10000 проблем, 100000 пар, 4 МиБ суммарного текста и JSONB, 10000 suspects на analysis и 1000000 операций по оценке `labels × sum(suspects)`. Консервативная верхняя оценка ответа ограничена 16 МиБ: она учитывает повтор кандидатов для каждой метки, верхние оценки строковых полей и шестикратное JSON-экранирование с запасом на служебные поля. Превышение возвращает 413 без усечения, даже если фактические совпадения дали бы меньший ответ. `analysis` должен быть объектом или null, `suspects` — массивом, null или отсутствовать; некорректный тип возвращает 500 с явной ошибкой до чтения инцидентов. Остальной JSON обрабатывается штатным Jackson, его ошибки не маскируются. `/api/evaluation/scenarios` отдельно ограничивает число различных сценариев до 1000 и длину каждого идентификатора до 1024 байт UTF-8; превышение возвращает 413 без усечения. Эти лимиты на запрос не ограничивают параллельные запросы, затраты PostgreSQL на сканирование и рендеринг JSONB либо общую память процесса; необходимы эксплуатационные ограничения. Проверки и чтение используют один снимок REPEATABLE READ.

### Неизменяемые снимки оценки

`POST /api/evaluation/runs` принимает только JSON вида `{"from":"2026-01-01T00:00:00Z","to":"2026-01-02T00:00:00Z"}` и возвращает 201 с `Location` и снимком. Время обязательно с часовым поясом, точность не выше микросекунд, границы от `1970-01-01T00:00:00Z` до `2100-01-01T00:00:00Z` включительно; полуинтервал `[from,to)` непустой и не более 31 суток. В окне допускаются до 1000 labels, до 1000 инцидентов и до 100 000 их пар; превышение возвращает 400 без усечения. Ошибки запроса возвращают 400 с `{"error":"..."}`. `GET /api/evaluation/runs?limit=50&offset=0` возвращает массив сводок (limit 1–100), `GET /api/evaluation/runs/{uuid}` — снимок или 404. Все маршруты защищены обычным `X-Advisor-Token`. Изменение и удаление через API не поддерживаются.

Снимок schemaVersion `1`, methodologyVersion `time-overlap-v1`: JSON содержит `id`, `createdAt`, `from`, `to`, версии, `scope: "window_approximation"`, `labels`, `incidents` и `report`. Labels содержат `scenarioId`, `faultId`, `type`, `source`, `start`, `end`; incident содержит `id`, `startedAt`, `analysisStatus`, `analysisPresent`, `completedAt`, упорядоченный `rankedSources` и `problems` с `startedAt` и техническими `hosts` только для первых по времени проблем (для baseline). Неоднозначный целочисленный `completedAt` без указанной единицы измерения сохраняется как `null`. `report` — сохранённый EvaluationReport с `rows`, кандидатами, сводными показателями и `outsideWindowIncidentIds`. Список возвращает только идентификатор, время, окно, версии и scope. В сохранённом JSON даты и Duration записаны как строки ISO-8601; представление HTTP зависит от настроек Jackson сервиса.

В транзакции REPEATABLE READ берутся все инциденты с началом в окне и все labels **всех сценариев**, у которых `[start,end + 2 минуты)` пересекает окно; затем вычисляется отчёт и вставляется снимок. Граница `to` исключена. Если кандидат попал в несколько labels, он неоднозначен; первый однозначный разобранный кандидат определяет метрики, baseline и время ответа. Инциденты вне окон labels в `outsideWindowIncidentIds` не считаются ложными срабатываниями. Полнота разметки не гарантируется; частично пересекающие окно сбои оцениваются только по наблюдаемой части. Связь определяется лишь временем, а не принадлежностью к конкретному запуску сценария. Панель «Точность» доступна администраторам в модуле Zabbix: она показывает снимки, сводку по типам сбоев и сравнение двух снимков. Результат обозначается как **приближение по окну** (window approximation), не как точная оценка запуска.

Для снимков технические строки меток и имена hosts/suspects ограничены 1024 байтами UTF-8; отдельные выборки JSON имён hosts и suspects ограничены консервативной оценкой по 4 МиБ до агрегации в SQL. Итоговая сериализация снимка ограничена 16 МиБ UTF-8. Превышение возвращает 400 без усечения и сохранения; эти лимиты могут отклонить ранее допустимое окно. Число инцидентов проверяется до чтения их analysis; обе операции выполняются в одной транзакции REPEATABLE READ.

Сохраняются только поля, необходимые для повторения текущей методики и отчёта, а не полный analysis, logEvidence, explanation, ошибки, имена триггеров, теги, причины или логи. Имена хостов, источники и идентификаторы сценариев сами могут быть чувствительными; доступ к API и БД следует ограничивать. Trade-off: snapshot позволяет повторить именно эту версию метрик, но не позволяет восстановить исходный разбор или объяснить его по логам; удаление исходных инцидентов его не меняет. Срок хранения снимков не ограничен текущим механизмом retention, поэтому требуется отдельная политика хранения/доступа на уровне эксплуатации. Непосредственный доступ на запись к БД может изменить снимки; API не предоставляет update/delete.

Форматы, защита и таблицы БД описаны в [модулях и контрактах](architecture/modules.md).
